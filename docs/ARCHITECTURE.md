# Архитектура CLAIR PRO

## 1. Принцип: независимость компонентов

CLAIR PRO собирает три самостоятельных сервиса в единый продукт, не размывая их границы:

```
             HTTP :8080                    HTTP :3000
┌───────────┐  ┌──────────────────┐   ┌─────────────────────┐
│ Пользоват.│─►│ CLAIR Gateway    │──►│ CLAIR Base (immutable)│
│ (UI/curl) │  │ validate→decide→ │   │ POST /compress        │
└─────┬─────┘  │ compress→forward │   └──────────┬────────────┘
      │        └────────┬─────────┘              │
      │ POST :4000      │ JSONL                  │ JSONL
      ▼                 ▼                        ▼
┌──────────────┐  logs/gateway.jsonl      logs/clair_pilot.log.jsonl
│  Dashboard   │◄─────────── read-only ─────────────┘
│ (UI+API)     │
└──────────────┘
```

Единственные интерфейсы между сервисами:
1. **HTTP**: `POST /compress`, `GET /health` (Base), `POST /v1/chat/completions` (Gateway), `GET /api/*` (Dashboard);
2. **JSONL-файлы**: Gateway и Base пишут операционные логи, Dashboard читает их **read-only**.

Ни один сервис не импортирует код другого. Dashboard никогда не пишет в логи. Gateway не знает о существовании Dashboard.

## 2. Слои

### 2.1 Orchestration Layer — `launcher.js`

Одна точка входа `clair-pro.bat|.sh → node launcher.js`. Обязанности:

| Шаг | Что делает | Как проверяет |
|---|---|---|
| 1. Base | находит `CLAIR_PILOT_DIR`, определяет точку входа (`dist/*.js` → `package.json main` → `scripts.start`; либо `CLAIR_START_CMD`), спавнит | poll `GET /health` до 25 с |
| 1b. Mock LLM (`--demo/--mock-llm`) | поднимает `llm-mock.mjs` на :4100 и настраивает `LLM_PROVIDER_URL` Gateway на него | poll `GET /v1/models` |
| 2. Gateway | спавнит из `CLAIR_GATEWAY_DIR`: через локальный `tsx` (dev) или `dist/main.js` (prod) | poll `/health` |
| 3. Dashboard | спавнит `dashboard/src/server.ts`, передаёт пути к обоим логам | poll `/health` |
| 4. Баннер + браузер | печатает адреса, открывает UI | — |

Ключевые решения:
- **Переиспользование**: перед спавном каждого сервиса проверяется, не отвечает ли уже его порт. Так launcher можно запускать параллельно с уже работающим стеком.
- **Чистое выключение**: дети стартуют в собственной POSIX-группе (на Windows — обычный процесс + `taskkill /T /F`), поэтому `Ctrl+C` гасит ровно то, что поднял launcher, включая внуков (`tsx → node`).
- **Аварийная семантика**: неожиданная смерть любого ребёнка или ошибка на старте останавливает весь стек — продукт никогда не остаётся в полурабочем состоянии.
- **Кроссплатформенность**: единственный исходник логики; `.bat`/`.sh` — обёртки по три строки. То, что отлажено на Linux, работает и на Windows.

### 2.2 Visual Dashboard — `dashboard/`

**Backend (`server.ts`, Express, TypeScript)** — тонкий слой над логами:

| Endpoint | Назначение |
|---|---|
| `GET /api/data?limit&session&cache&source&q&from&to` | агрегаты + строки таблицы + мета файлов одним ответом |
| `GET /api/export.csv|.json` | экспорт с теми же фильтрами (CSV: UTF-8 BOM для Excel) |
| `GET /api/events` | SSE: опрос size/mtime обоих логов раз в 2 с, событие `update` при росте |
| `POST /api/test-request` | прокси на Gateway `POST /v1/chat/completions` + прикрепление свежей записи лога как «метрик» |
| `GET /health` | проверка живости |

**Ядро разбора (`stats.ts`)** — чистые функции без HTTP:
- `readJsonl(file, kind)` — толерантное чтение JSONL (битые строки считаются `corruptedLines`, не падают);
- нормализация обоих форматов в `UnifiedEntry`;
- вывод статуса кэша: `BYPASS` (сжатие выключено) / `HIT` / `PARTIAL` / `MISS` (из счётчиков `cache_hits`/`cache_misses`), для Base — `null`;
- `aggregate()` — totals, срезы по дню/часу/сессии/режиму/модели, перцентили задержек;
- `toCsv()` — сериализация с экранированием.

**Frontend (`public/`, vanilla JS без сборки)**:
- один `fetch('/api/data')` на обновление — атомарный снимок состояния;
- Chart.js 4 (UMD-файл в `vendor/`) — четыре графика; инстансы обновляются через `chart.update()`, без пересоздания;
- `EventSource('/api/events')` → debounce 400 мс → перезагрузка данных (real-time);
- фильтры формируют query-string — серверная фильтрация, клиент не дублирует логику;
- темы через CSS-переменные (`data-theme`), сохранение в `localStorage`;
- экспорт — обычная навигация на `/api/export.*?filters`.

### 2.3 Почему Dashboard читает логи, а не опрашивает API

Логи — уже существующий публичный контракт обоих сервисов (и единственный для immutable Base). Чтение файлов:
- не требует изменений в Gateway/Base;
- устойчиво к рестартам сервисов (данные сохраняются);
- даёт полную историю, а не только текущий процесс.

Плата за это — задержка до 2 с на real-time (poll), что для метрик несущественно.

## 3. Потоки данных

**Сквозной тестовый запрос из UI:**
1. пользователь вводит текст → `POST /api/test-request` (Dashboard);
2. Dashboard → `POST :8080/v1/chat/completions` (Gateway);
3. Gateway: validate → decide → `POST :3000/compress` (Base) → подстановка сжатого текста → LLM;
4. Gateway пишет строку в `gateway.jsonl`, Base — в `clair_pilot.log.jsonl`;
5. Dashboard находит свежайшую запись лога и возвращает UI: ответ LLM + чипы метрик;
6. SSE сообщает всем открытым вкладкам об обновлении логов → таблица и графики перерисовываются.

## 4. Границы и гарантии

| Правило | Как обеспечено |
|---|---|
| CLAIR Base immutable | в `clair-pro/` нет кода, пишущего в `CLAIR_PILOT_DIR`; Base только спавнится по готовой точке входа и вызывается по HTTP; его лог читается read-only |
| Gateway не модифицируется | репозиторий подключается каталогом/образом «как есть»; все адаптации (пути, порты, LLM) — через переменные окружения при запуске |
| Нет БД и облака | единственное хранилище — JSONL-файлы; сеть: localhost + настроенный LLM; Chart.js завендорен |
| Никаких «тяжёлых» фреймворков | Dashboard: Express + vanilla JS; сборка — один `tsc` |

## 5. Тестовая пирамида

1. **14 юнит-тестов** (`dashboard.test.ts`): нормализация двух форматов логов, агрегаты, фильтры, экспорт, прокси с фейковым upstream, устойчивость к битым строкам и отсутствующим файлам.
2. **6 e2e-тестов** (`orchestration.test.ts`): полный стек через `launcher.js --demo` на изолированных портах — старт одной командой, health всех сервисов, сквозной запрос с реальной экономией токенов, агрегация в Dashboard, экспорт, `SIGINT` без «зомби».
3. **`scripts/smoke.sh`** — быстрый прогон живого стека для ручной приёмки (порты по умолчанию).

## 6. Известные компромиссы

- **Poll вместо inotify/FSWatcher**: `fs.watch` ведёт себя по-разному на Windows/Linux; 2-секундный опрос size+mtime даёт одинаковое поведение везде.
- **Session в Gateway статична** (`SESSION_NAME`): per-request сессии не предусмотрены контрактом Gateway v1.1.0; сессионная аналитика ведётся по полю `session` логов (как и задумано в ТЗ).
- **Docker и Windows-пути**: volume-монтаж `c:\Clair_pilot` зависит от Docker Desktop; Node-лаунчер — путь без этого риска.
